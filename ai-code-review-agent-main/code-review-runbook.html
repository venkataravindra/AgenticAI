Execution Runbook

AI Code Review Agent — how a request actually runs

Four independent services turn an uploaded file, or a public GitHub / Bitbucket URL, into a structured, LLM-backed review. This is a trace of that execution, captured from a real run of this build — not a mockup.

  • FastAPI
  • LangGraph
  • LangChain
  • ChromaDB
  • MCP
  • React + Vite
  • OpenAI gpt-4o-mini

Service topology

Each service owns one job and runs on its own port. The backend is the only one that talks to all three of the others.

:8001Config ServerSingle source of truth for LLM / RAG / MCP settings. Never returns the real API key.
:8002MCP ServerExposes code_metadata and code_analysis — deterministic, non-LLM checks.
:8000BackendFastAPI + LangGraph. Orchestrates the review, holds uploads and results in memory.
:5173FrontendReact + Vite. Upload files, or a repo URL, then read the result.

Two ways in, one pipeline

Uploading files and submitting a repo URL are different on the way in, and identical from here on — the diagram below is the proof, not just the claim.

Guardrails on the repo-URL path: host allowlist (github.com / bitbucket.org only), http(s)-only, no embedded credentials, git clone --depth 1 via an argument list (never a shell string), a clone timeout, and a per-file size cap plus a 30-file ceiling so one giant repo can't blow out the review or the LLM prompt.

STEP 01

Environment setup

Four services, four virtual environments. Each gets its own .env copied from its .env.example.

setup.sh
cd config-server && python -m venv .venv && ./.venv/bin/pip install -r requirements.txt
cd ../mcp-server    && python -m venv .venv && ./.venv/bin/pip install -r requirements.txt
cd ../backend       && python -m venv .venv && ./.venv/bin/pip install -r requirements.txt
cd ../frontend      && npm install

# each service: cp .env.example .env, then fill in OPENAI_API_KEY

What actually happened on this run (Windows, Python 3.14 pre-installed): the pinned numpy/pydantic-core/chroma-hnswlib versions ship no prebuilt wheel for 3.14, and the box had no C++ toolchain. Fix, in order: installed Python 3.12 side-by-side via winget, rebuilt every venv against it, then installed VS Build Tools (C++ workload) to compile chroma-hnswlib from source — the one native dependency with no Windows wheel at any version. No requirements.txt pin was changed.

STEP 02

Launch sequence

Order matters a little: Config Server and MCP Server should be up before the first /api/review call, since that's when the backend reaches out to both.

4 terminals
# 1 — Config Server
cd config-server && ./.venv/bin/uvicorn app.main:app --port 8001

# 2 — MCP Server
cd mcp-server && ./.venv/bin/python server.py

# 3 — Backend (ingest once, then serve)
cd backend && ./.venv/bin/python -m app.rag.ingest
cd backend && ./.venv/bin/uvicorn app.main:app --port 8000

# 4 — Frontend
cd frontend && npm run dev

STEP 03

Trace — reviewing an uploaded file

A deliberately buggy two-function file, pushed through the real API — no mocking.

sample.py
def add(a, b):
    return a+b

def divide(a, b):
    return a / b  # no zero check
curl
curl -X POST :8000/api/files/upload -F "files=@sample.py"
{"upload_id":"b7017a51-...","files":["sample.py"]}

curl -X POST :8000/api/review -d '{"upload_id":"b7017a51-...","file_names":["sample.py"],"review_focus":"general"}'

What the graph did, node by node

  • 1
    validate_code — confirmed .py is a supported extension.
  • 2
    retrieve_context — similarity search over the 18 ingested chunks. Result: rag_context_used: true.
  • 3
    run_mcp_tools — called both MCP tools over streamable-HTTP. Result: mcp_tools_used: ["code_metadata", "code_analysis"].
  • 4
    review_code — ChatOpenAI(gpt-4o-mini) with with_structured_output(ReviewResult), prompted with the code + RAG context + MCP results.
  • 5
    format_response — attached the RAG/MCP flags, assigned a review_id.

Actual response

SevCategoryLineFinding

mediumquality6No spacing around the / operator.

Score 60 / 100 · the planted divide-by-zero bug was caught on the first pass, unprompted.

Guardrails, exercised for real

rejected inputs
ftp://github.com/psf/requests
-> Only http:// or https:// repository URLs are supported.

https://evil.example.com/psf/requests
-> Unsupported host 'evil.example.com'. Only GitHub and Bitbucket URLs are supported.

https://user:pass@github.com/psf/requests
-> Repository URLs with embedded credentials are not supported.

https://github.com/this-user-does-not-exist-xyz/this-repo-does-not-exist-abc
-> Could not clone repository: fatal: repository not found

Every rejection happens before a clone is attempted — the URL is validated first, so a bad host or scheme never reaches git.
